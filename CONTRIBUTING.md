# Contributing to Turbogol

Thanks for helping! Turbogol is a community project: code, bug reports, playtesting, translations,
art direction, bot tuning and documentation are all welcome. This guide explains how to get set up
and what we expect from a pull request. By participating you agree to follow our
[Code of Conduct](CODE_OF_CONDUCT.md).

> Turbogol is an original game. Please do not contribute anything taken from commercial games:
> no names, logos, textures, models, sounds, screenshots, collision meshes, map layouts or
> numbers measured from another game. Everything in this repository is generated by our own code.
> If in doubt, open an issue first.

## Ways to help

- **Play and report bugs:** use the *Bug report* form under Issues. Include your browser, GPU, and
  what you did right before it happened.
- **Pick an issue:** look for the labels `good first issue` and `help wanted`.
- **Propose a feature:** open a *Feature request* or start a Discussion before writing a big change,
  so we can agree on the design first.
- **Translate:** add your language in one file, see [Translating](#translating) below.
- **Chat with us:** join the [Turbogol Discord](https://discord.gg/sPyf787aHP) to ask questions, find
  people to playtest with and talk about ideas. Bugs and feature requests still go through Issues.

## Development setup

Requirements: Node.js 24+, git, and a browser with WebGPU (or at least WebGL2).

```sh
git clone --recurse-submodules https://github.com/DonJaimeHash/turbo-gol.git
cd turbo-gol
npm install
npm run dev            # the game at http://localhost:5173 (offline modes work without the backend)
```

Online modes run against a local backend (no Cloudflare account needed):

```sh
cd server && npm install && cp .dev.vars.example .dev.vars   # then set JWT_SECRET to any long random string
npm run dev            # wrangler dev on http://127.0.0.1:8787; Vite proxies /api, /ws, /room and /lobby to it
```

The physics engine is prebuilt (`src/sim/wasm/rocketsim.wasm` is committed). You only need the
Emscripten SDK if you change the C++ wrapper or the physics library: see `native/README.md`.

## Translating

The game follows the player's system language when it ships it, and falls back to English. Every
text lives in `src/locales/`: `en.ts` is the source of truth, `es.ts` is neutral Latin American Spanish
(`tú`, no regional slang). To add a
language (say French, code `fr`):

1. Copy `src/locales/en.ts` to `src/locales/fr.ts`. Replace its header import with
   `import type { Translation } from '../i18n';` and change the last line to
   `} satisfies Translation;` (see `es.ts`). A locale file may only use `import type`.
2. Translate the values. Keep every key and every `{placeholder}` as it is. Delete the lines you do
   not translate yet: they fall back to English, so a partial translation is fine.
3. Plurals are objects: give the forms your language uses from
   [Intl.PluralRules](https://www.unicode.org/cldr/charts/latest/supplemental/language_plural_rules.html)
   (`one`, `few`, `many`, `other`...); `other` is always required.
4. Keep texts short: the menus must fit a 375 px wide phone.
5. Register the language with one line in `LOCALES` in `src/i18n.ts`, using its own name:
   `fr: { name: 'Français', messages: fr },` (plus the `import fr from './locales/fr';` next to the others).
6. Run `npm run typecheck && npm test`, try it with your browser set to that language (or pick it
   in the menu), and open a pull request.

Names from commercial games (game titles, studios, mode names) must not appear in translations
either; see [TRADEMARKS.md](TRADEMARKS.md).

## Before you open a pull request

Run the same checks as CI:

```sh
npm run typecheck && npm test                 # client: types + node tests (sim, bots, net, menus...)
cd server && npm run typecheck && npm test     # backend: types + unit tests
```

Online changes should also pass the end-to-end smokes against `wrangler dev`
(`node server/test/smoke.mjs`, `smoke-p2p.mjs`, `smoke-accounts.mjs`).

Pull request checklist:

1. One topic per PR, with a clear description of *what* and *why* (screenshots / clips for visual changes).
2. Tests for logic changes. The simulation must stay **deterministic**: online play compares state
   hashes between peers and the server, so never add randomness, time or iteration-order
   dependencies to the tick path.
3. Keep the per-frame paths allocation-free (see the comments in `src/game/Game.ts` and `src/render`).
4. Match the surrounding code style: TypeScript strict, small focused modules, comments that explain *why*.
5. Update the docs (`ARCHITECTURE.md`, `docs/`) when you change behaviour or a protocol.
6. Sign off every commit (see below).

## Developer Certificate of Origin (DCO)

We use the [Developer Certificate of Origin](https://developercertificate.org/) instead of a CLA.
By adding a `Signed-off-by` line to your commits you certify that you wrote the change or
otherwise have the right to submit it under the project's license:

```sh
git commit -s -m "Fix the goal replay camera"
```

## Project layout

`ARCHITECTURE.md` describes every module and its owner. In short: `src/sim` (physics bridge and
field constants), `src/game` (game loop, match rules, training), `src/render` (three.js renderer and
HUD), `src/ai` (bots), `src/net` (online client: P2P rollback, server client, accounts, lobbies),
`src/ui` (menus), `server/` (Cloudflare Workers backend), `native/` (C++ wrapper around the physics
library), `tests/` (node tests).

## Releases

Maintainers tag releases as `vX.Y.Z` following [Semantic Versioning](https://semver.org/) and keep
`CHANGELOG.md` up to date ([Keep a Changelog](https://keepachangelog.com/) format).
